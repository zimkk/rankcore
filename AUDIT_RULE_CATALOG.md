# RankCore Audit Rule Catalog

Verified: 2026-09-21  
Status: canonical initial deterministic rule specification  
Principle: high-confidence, explainable checks before rule count

## Rule contract

Every deterministic finding should include:

- stable `rule_id`;
- severity;
- confidence;
- URL/entity;
- concise message;
- observed evidence;
- why it matters;
- verification condition;
- optional remediation hint;
- source/reference key when platform-specific.

Severity is not a synthetic SEO score.

Recommended severity:
- `critical` — widespread eligibility/destructive configuration failure;
- `high` — clear technical failure likely to impair intended discovery/indexing;
- `medium` — meaningful inconsistency or broken user/search path;
- `low` — useful but non-urgent issue;
- `info` — contextual observation requiring judgment.

## P0 — Eligibility / catastrophic misconfiguration

### RC-HTTP-001 — Intended public page returns persistent 5xx
Evidence: final response status/repeated fetch result.  
Verification: URL returns intended successful response.

### RC-ROBOTS-001 — robots.txt blocks intended public search surface
Evidence: RFC-compliant rule evaluation for target crawler.  
Context: only high severity when product profile says the surface should be discoverable.  
Verification: target becomes crawl-allowed or profile is corrected.

### RC-INDEX-001 — Intended public page is explicitly noindexed
Evidence: robots meta/X-Robots-Tag.  
Context required.  
Verification: noindex removed where indexing is intended.

### RC-CANON-001 — Sitewide/widespread canonical points to wrong domain/environment
Evidence: canonical targets across representative/indexable pages.  
Severity: critical when systemic.  
Verification: canonical targets align with intended public host.

### RC-REDIRECT-001 — Redirect loop prevents public page retrieval
Verification: request resolves to intended final URL without loop.

### RC-RENDER-001 — Primary intended content unavailable in rendered DOM
Only in rendered mode and only when raw/loaded state shows a real failure.  
Do not flag ordinary progressive enhancement.

## P1 — HTTP / URL hygiene

### RC-HTTP-002 — Internal public page returns 4xx unexpectedly
### RC-HTTP-003 — Excessive redirect chain
Use configurable threshold; do not pretend a single redirect is harmful.
### RC-HTTP-004 — Soft-404 candidate
Require multiple signals and label confidence.
### RC-URL-001 — Duplicate URL variants expose same page without clear consolidation
Examples: protocol/host/slash/case/parameter variants when demonstrable.

### RC-META-002 — Empty/obvious placeholder title
### RC-META-003 — Substantial duplicate-title cluster across distinct intended pages
### RC-META-004 — Missing meta description

## P1 — Structured data / entity consistency

### RC-SCHEMA-001 — Invalid JSON-LD syntax
### RC-SCHEMA-002 — Invalid/impossible type/property shape for configured validation scope
### RC-SCHEMA-003 — Structured data contradicts visible/source-of-truth content
### RC-SCHEMA-004 — Conflicting entity identity
### RC-SCHEMA-005 — Markup references broken/noncanonical identity URL
### RC-SCHEMA-006 — Fabrication-risk field candidate

## P2 — AI/search crawler access

### RC-AI-ROBOTS-001 — AI search/retrieval crawler policy summary
Informational by default. Report purpose-specific policy, not a single “AI allowed” boolean.

### RC-AI-ROBOTS-002 — User-selected search-discovery crawler is blocked
Only warn when the user/project policy explicitly intends visibility on that surface and the crawler purpose is currently verified from official vendor docs.

### RC-AI-ROBOTS-003 — Training crawler policy
Informational only. Never flag blocking training as an SEO error.

### RC-LLMS-001 — Published llms.txt is malformed for selected proposal/version
Run only if file exists or feature is explicitly enabled.
### RC-LLMS-002 — Published llms.txt links to private, broken, or clearly noncanonical URLs
Low/medium depending leakage risk.
### RC-LLMS-003 — Missing llms.txt
**Do not implement as a failure.** Absence is not an SEO error.

## P2 — Content-surface candidates

These are evidence candidates for agent interpretation, not autonomous “failures.”

### RC-CONTENT-001 — Near-duplicate intended indexable page cluster
### RC-CONTENT-002 — Page intended for an informational job has extremely little retrievable information
Requires intent/profile context.
### RC-CONTENT-003 — Product/entity identity is ambiguous on a primary public page
### RC-CONTENT-004 — Comparison/claim page contains potentially stale external facts
Candidate for current-source review, not deterministic truth.
### RC-CONTENT-005 — Large programmatic page cluster with very low differentiated content signals
Never auto-noindex/delete; escalate for value review.

## P2 — Performance / experience

### RC-PERF-001 — Missing intrinsic image dimensions likely to cause layout instability
### RC-PERF-002 — Very large same-origin/client JS transfer candidate
Use configurable diagnostics, not universal ranking threshold.
### RC-PERF-003 — Reliable connected field CWV is poor
Only when field data is actually connected and source/date are known.
### RC-PERF-004 — Lab performance regression
Diagnostic only; never present one lab run as field truth.

## P2 — Accessibility / agent interoperability

### RC-A11Y-001 — Interactive control lacks accessible name
Rendered mode.
### RC-A11Y-002 — Link/button purpose is empty/ambiguous to accessibility tree
Rendered mode.
### RC-A11Y-003 — Form control missing associated label where deterministically detectable

These are user/accessibility/agent-readiness issues, not “ranking points.”

## Rule behavior requirements

### Context awareness

Before high-severity findings, determine whether URL is:
- public marketing/content;
- private/authenticated;
- account/checkout;
- staging;
- duplicate/parameter;
- utility/API;
- intentionally retired.

### Confidence

Use confidence levels such as:
- high — directly observed, unambiguous;
- medium — evidence strong but intent/context uncertain;
- low — heuristic candidate needing agent/human review.

### Evidence

Store enough evidence to re-test:
- status;
- directive;
- source URL;
- target URL;
- selector/header where relevant;
- crawl path;
- raw structured-data error;
- canonical/hreflang relation.

### Verification

Every fixable rule needs a deterministic pass/fail re-check where possible.

## Rules intentionally excluded

Do not add these as canonical failures:

- keyword-density thresholds;
- exact title character-count rules;
- exact meta-description character-count rules;
- mandatory exactly-one-H1 rule;
- arbitrary word-count minimums;
- “DA/DR too low”;
- mandatory FAQ schema;
- missing llms.txt;
- backlink quantity targets;
- keyword-in-every-heading checks;
- arbitrary “SEO score” deductions;
- “must use SSR” without evidence;
- “must allow AI training crawlers”;
- “must create X blog posts per month.”

## Initial implementation priority

Ship fewer reliable rules before many heuristics.

Suggested first tranche:

1. HTTP 5xx/4xx and redirect loops;
2. robots evaluation;
3. meta/header noindex;
4. canonical extraction/target validation;
5. sitemap parsing/consistency;
6. broken internal links;
7. title/description presence;
8. JSON-LD syntax;
9. hreflang validity/reciprocity;
10. AI crawler policy classification;
11. baseline verification.

Rendered/accessibility/performance heuristics come after HTTP-mode correctness.
